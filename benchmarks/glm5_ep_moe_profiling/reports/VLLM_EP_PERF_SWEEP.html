So the clean comparable grid is EP4 (4 backends) + EP8 single-rack (NCCL) + the sglang-NCCL baseline.

Reproduced HTML insights. ① a2a latency-bound: dispatch ~flat across bs at fixed EP (nvlink EP4 9→13µs over bs1→128). ③ moe_compute ~flat 9-10µs, EP-independent. ⑤ dtype: moe_compute identical across backends (same NVFP4 FP4 GEMM). NEW cross-framework: vLLM allgather ≈ sglang none (same NCCL kernels, dispatch within ~10%). NEW divergence: none of vLLM’s working backends reproduce DeepEP-LL’s flat ~12µs EP-scaling — NCCL allgather rises 22→40µs (EP4→8) and explodes cross-rack.

FP8 + DeepEP-LL attempt (to reproduce the HTML's true DeepEP-LL grid). FP8 GLM-5 weights route MoE through BatchedDeepGemmExperts (= sglang's deep_gemm FP8 path, no broken CUTEDSL) — this SOLVED the expert-backend crash. But: (1) FP8 (705GB) OOMs on EP4 (4×184GB), needs EP8+; (2) EP8 FP8 + deepep_low_latency single-rack (job 3272018, nvl72022) hit the SAME cross-node wall as NVFP4 EP8: deep_ep.cpp:226 'invalid resource handle' (cudaIpc handle can't cross nodes). Conclusion: DeepEP cross-node (EP8+) is impossible on this cluster regardless of dtype — a host-fabric (MNNVL/IMEX channel) configuration gap, not a code/dtype issue. DeepEP works only single-NODE (EP4) here. Reproducing the HTML's full DeepEP-LL EP4-64 grid needs cluster admins to enable GB200 MNNVL/IMEX (the same blocker the sglang runbook documents).
